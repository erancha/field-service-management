## Working copy location

Keep the checkout on the WSL ext4 filesystem (`~/projects/python/field-service-management`)
rather than under `/mnt/c`. WSL reaches Windows drives through a file-sharing protocol that makes
every file open a round trip to the Windows side, and the virtualenv installs, `npm ci` and the
test runs open thousands of files.

## Frontend

`deploy.sh` builds the page into the edge's image, which serves it on all three role ports. For
work on the page, `npm run dev` in `frontend/` serves it with hot reload at
http://localhost:5173 and proxies `/api`, `/auth` and `/calendar` to the technician role at
http://localhost:8001, so the stack must be up. [frontend/README.md](../frontend/README.md) has
the details.

## Configuration

`./scripts/init-env.sh` creates the gitignored `secrets.sh`, `params.sh` and `aws-config.sh`
under `scripts/lib/` from [secrets.example.sh](../scripts/lib/secrets.example.sh),
[params.example.sh](../scripts/lib/params.example.sh) and
[aws-config.example.sh](../scripts/lib/aws-config.example.sh), keeping a file that already
exists; each setting's comment says what it holds and whether it is required. `deploy.sh` runs
it first on every run, and stops with a list of every setting it needs that is still blank.

- `secrets.sh` — the database password, the session secret, the token key that encrypts the
  technicians' Google refresh tokens and the photo store's secret key, all generated by
  `init-env.sh`, the database URL built from the password, the Google client's secret, and the
  optional model provider, SMTP and Google API keys.
- `params.sh` — this deployment's own settings that are no secret: `GOOGLE_CLIENT_ID`
  ([Sign-in](sign-in.md#setting-up-google) sets up the Google client), `ADMIN_EMAILS`, the
  assistant's models, the SMTP relay and account, and the author's address.
- `aws-config.sh` — the access key pair and region of the AWS account `deploy.sh --ec2`
  deploys to; a machine that deploys only locally leaves it unfilled.

Every other setting is committed in [stack-params.sh](../scripts/lib/stack-params.sh): the
ports, the database name, the EC2 stacks' names, the host forms of the Redis and object-store
addresses, and the optional keys at their defaults. Sign-in needs `GOOGLE_CLIENT_ID`,
`GOOGLE_CLIENT_SECRET` and `SESSION_SECRET`, so `deploy.sh` refuses to start without them. An
edit to any of the three files takes a `deploy.sh` run. A new `FSM_TOKEN_KEY` makes every stored
calendar connection unreadable, so `init-env.sh --force` is for a fresh start only.

A script that loads a settings file first stops if git would track it, or a tracked file holds
one of its secrets or email addresses, the commercial-license contact of `params.sh`
(`LICENSE_CONTACT`, the one setting `scripts/lib/settings-guard.sh` admits) excepted. It also
sets `core.hooksPath` to `.githooks`, whose `pre-commit` hook makes the same check on every
commit's staged changes.

The scripts export the three files into their shell before calling Compose, so a bare
`docker compose` call has no settings. The files hold the host forms of `DATABASE_URL`,
`REDIS_URL` and `MINIO_ENDPOINT`; Compose overrides them with the in-network addresses. A
backend process started on the host runs from the repo root, because it reads the settings files
by their path from the working directory.

## Backend tests

[`test.sh`](../scripts/test.sh) is the whole quality gate. It runs the backend and the frontend
by default, or the targets named: `backend` runs the scripts' syntax check and their shell tests
under `scripts/tests/`, ruff, mypy, the import-linter layer contracts and pytest, whose
integration tests start a throwaway Postgres and object store through Testcontainers, so Docker
must be running; `frontend` runs oxlint, Vitest, the TypeScript check and the Vite build. It
needs Python 3.12+, and creates `backend/.venv` on its first run; Node.js 22 for the page. No
test needs a model key or a Google client. The GitHub Actions workflow runs the backend and the
frontend.

`./scripts/test.sh e2e` is opt-in: it builds and starts the `samples/redis_event_bus_with_sse/`
stack and checks that a message crosses two backend processes through Redis before it returns
over the event stream. [Testing](testing.md) states what each layer proves.

`backend/tests/test_requirements_lock.py` fails until `backend/requirements.txt` matches
`backend/pyproject.toml` and the image; `tools/lock.sh` brings it back in line.

## Deployment scripts (`scripts/`)

Docker runs the stack; `deploy.sh` and `docker-helper.sh` stop when it is not reachable.

- [`deploy.sh`](../scripts/deploy.sh) — builds the images, starts Postgres (with its schema
  migration), Redis, the object store, the role replicas, the calendar worker and the nginx
  edge in Docker, and returns once each role answers through the edge. Then open the back
  office at http://localhost:8003 and sign in with a Google account listed in `ADMIN_EMAILS`
  and as a test user of the Google client.
- `deploy.sh --ec2` — the same on an EC2 instance, as one stack per role
  ([The EC2 stack](#the-ec2-stack)).
- [`docker-helper.sh`](../scripts/docker-helper.sh) — `--stop [--volumes]`,
  `--logs [-e|-w] [--grep <pattern>] [--since <duration>] [--sorted] [service...]` or `--ps` for
  the stack; `--volumes` also removes the database and the photos. With `--ec2` as its first
  argument it acts on the instance, and `--ec2 --delete-stack` deletes this repo's three EC2
  stacks.
- [`test.sh`](../scripts/test.sh) — the quality gate and the e2e, above.
- [`init-env.sh`](../scripts/init-env.sh) — creates the settings files, above; `--force`
  replaces existing ones, hand-filled keys and the generated keys included.
- `tools/` — hands-on tools: [`sql-helper.sh`](../scripts/tools/sql-helper.sh) (psql on the
  stack's database: a shell, `-c`, a SQL file, row counts and rows of every table, and
  `--backup <file>` and `--restore <file>` of the whole database; `--ec2` first acts on the
  instance), [`lock.sh`](../scripts/tools/lock.sh) (recompiles `backend/requirements.txt` inside
  the Dockerfile's Python image; run it after editing the dependency list) and
  [`release.sh`](../scripts/tools/release.sh) (tags the next version and pushes the tag, which
  the CI workflow publishes as a GitHub Release once the tests pass).
  [`tools/README.md`](../scripts/tools/README.md) lists them.

`scripts/common.sh` holds what the scripts share: the repo paths, the help printer, the loader
of the settings files, the three roles with their ports and EC2 stacks, Compose access, and the
backend virtualenv setup. `lib/settings-guard.sh` keeps the gitignored files' values out of git,
and `lib/ec2.sh` holds the EC2 target: a stack's deploy, the SSH connection with an EC2 Instance
Connect key, and Compose pointed at the instance's Docker daemon. Both, the template and the
pre-commit hook are the same files in every Docker Compose repo, and each serves one stack at a
time; `select_ec2_role` of `common.sh` points them at each role's stack in turn.

## The EC2 stack

`deploy.sh --ec2` deploys to an EC2 instance in the account of `aws-config.sh`. With
`EC2_HOST_STACK` of `params.sh` blank, the technician's stack is the instance's host and the other
two roles' stacks its guests. Set to another Docker Compose repo's host stack, all three are
guests on that instance, which is deployed first from its repo; `aws-config.sh` then names that
stack's account and region, since a guest's stacks import the host stack's exports
([ADR 0002](adr/0002-any-docker-repo-can-host-the-instance.md)).
It needs the AWS CLI, `ssh` and `curl`. It creates or updates one CloudFormation stack of
[`template-ec2.yaml`](../scripts/template-ec2.yaml) per role (the role's edge port on the instance
and a CloudFront distribution), builds the images here for ARM, loads them into the instance's
Docker daemon over SSH and starts the stack there with
[`docker-compose.ec2.yml`](../docker-compose.ec2.yml), and prints each role's CloudFront address
and the redirect URIs to register with Google ([Sign-in](sign-in.md#setting-up-google)). The git
branch selects the stacks: `main` deploys `field-service-management-tech`, `-app` and `-admin`,
any other branch the same names with `-fb` on the host's `-fb` instance. An exported `STACK_NAME`,
which names a single stack, is refused. Every deploy, host or guest, also makes sure the instance
has a 1 GB swap file (`prepare_ec2_host` in `lib/ec2.sh`), so a burst beyond the instance's 2 GB
of memory slows the stacks instead of killing a container.

Each role needs a distribution of its own because the roles are told apart by their origin: a
sign-in's role comes from the app it completes at, and the session cookie belongs to one host.
Compose runs on this machine against the instance's daemon, so nothing in the stack is
bind-mounted from this machine: the edge's configuration and the built page are baked into its
image, and the database and the photos live in named volumes. On the instance each role builds
its Google callbacks from its own CloudFront address, set in `docker-compose.ec2.yml`, since
CloudFront reaches the edge over plain HTTP and a callback derived from the request would name
http; `APP_ENV=prod` marks the session cookie Secure.

`docker-helper.sh --ec2 --delete-stack` deletes this repo's three EC2 stacks after asking for
each one's name: its port on the instance and its distribution. The containers and the volumes
stay on the instance, so run `docker-helper.sh --ec2 --stop` (with `--volumes` to drop the data)
first; `tools/sql-helper.sh --ec2 --backup <file>` keeps a copy of the database on this machine.

The IAM user of `aws-config.sh` needs to create and delete the stacks' resources
(CloudFormation, security group rules, CloudFront distributions), to update the host stack's SSH
rule, and `ec2-instance-connect:SendSSHPublicKey` for the SSH connection. No IAM user has these
by default; an administrator has them all.

## Addresses

Each service has a port inside the Compose network, where the services reach each other by name;
the edge and the data services are also published on this machine. As shipped in
`scripts/lib/stack-params.sh`:

| Service | On this machine | Inside the Compose network |
|---|---|---|
| Edge, technician app | `http://localhost:8001` (`EDGE_TECHNICIAN_HOST_PORT`), on every interface | `nginx:8001` |
| Edge, customer app | `http://localhost:8002` (`EDGE_CUSTOMER_HOST_PORT`), on every interface | `nginx:8002` |
| Edge, back office | `http://localhost:8003` (`EDGE_BACKOFFICE_HOST_PORT`), on every interface | `nginx:8003` |
| Role replicas | not published; reached through the edge | `technician:8001`, `customer:8002`, `backoffice:8003` |
| Postgres | `127.0.0.1:5432` (`DB_HOST_PORT`), for `tools/sql-helper.sh`, a psql or a backend run on the host | `db:5432` (`DB_PORT`) |
| Redis | `127.0.0.1:6379` (`REDIS_HOST_PORT`), for a backend run on the host | `redis:6379` |
| Object store | `127.0.0.1:9100` (`OBJECT_STORE_HOST_PORT`), for a backend run on the host | `objectstore:9000` |

Every role answers `/` (the page), `/docs` (the API documentation), `/health` and `/ready`. A
published port must be free on this machine; change it in `stack-params.sh` if it is not. A new
edge port needs the same change in the Google client's redirect URIs
([Sign-in](sign-in.md#setting-up-google)). On the EC2 instance each edge port is the origin of
its role's CloudFront distribution, where only CloudFront reaches it, and the data services stay
on the instance's loopback interface. None of these ports is one the other stacks on the instance
publish: loan-simulator's 8100 to 8102, home-finance-agent's 8010 and 5434, amex-agent's 8020 and
cal-agent's 8030.

## Running the roles on the host

For fast restarts and a debugger, a role can run as a process on this machine against the
stack's data services, with the edge and the role replicas stopped so the processes take the
role ports. Run it from the repo root, where it reads the settings files; `FSM_ROLE` picks the
role and `FSM_FRONTEND_DIST` serves the built page:

```bash
./scripts/deploy.sh                                   # data services up, schema migrated
bash -c 'source scripts/common.sh && compose stop nginx technician customer backoffice worker'
(cd frontend && npm ci && npm run build)
FSM_ROLE=technician FSM_FRONTEND_DIST=frontend/dist backend/.venv/bin/uvicorn \
  fsm.platform.app:create_app --factory --port 8001
```

Start the other roles the same way on their ports (`customer` on 8002, `backoffice` on 8003),
and the calendar loops with `FSM_ROLE=worker backend/.venv/bin/python -m fsm.platform.worker`.
Each process shares the stack's Redis, so live events cross them as they cross the replicas.
`backend/.venv` comes from `./scripts/test.sh backend`. `./scripts/deploy.sh` brings the edge and
the replicas back.
